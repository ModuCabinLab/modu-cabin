# 시연 샘플 구조

`Cabin`이 프로필, 좌석 연결, 탑승 세션, 임시 요청, 제안, 최근 읽기값을 관리합니다. `plan()`은 실제로 연결된 탑승자의 풍량 허용 범위 교집합과 좌석별 설정을 계산합니다. 현재 가상 차량은 좌석별 온도를 지원하고 열선은 앞좌석만 지원합니다.

`vehicles`와 차종별 레이아웃은 아이오닉 5의 5석, 아이오닉 9의 6/7석, 팰리세이드의 7/9석을 정의합니다. 같은 7인승도 아이오닉 9는 2+3+2, 팰리세이드는 2+2+3입니다. `setVehicle()`은 차종과 정원을 먼저 검증하고 새 탑승을 시작합니다. 화면과 gateway를 동일한 vehicleId/capacity로 생성합니다.

`layouts`는 4=2+2, 5=2+3, 6=2+2+2, 7=2+3+2, 8=2+3+3의 예시 좌석 구성을 정의합니다. `setLayout()`은 정차·유휴 상태에서만 허용하며 새 탑승과 가상 초기 상태를 만듭니다. UI는 같은 정원의 gateway를 다시 생성합니다. `connectAll()`은 A~I를 중복 없이 연결하고, `move()`는 없는 좌석과 다른 탑승자가 점유한 좌석을 거부합니다.

`SimulationGateway`는 지연된 쓰기와 읽기를 제공합니다. 정상, 쓰기 실패, 읽기 불가, 읽기값 불일치를 선택할 수 있습니다. 실제 차량 SDK의 구현체가 아닙니다.

화면 초기화와 차종 변경 시 `capabilities()`로 시뮬레이터의 풍량 범위·온도 좌석·열선 좌석을 읽고 `Cabin.setCapabilities()`에 전달합니다. 지원 범위 변경은 기존 제안을 무효화합니다. `plan()`은 지원되는 명령만 만들고 비어 있는 열선 지원 좌석에는 0을 요청합니다. 이동 자체가 열선을 끄는 것은 아니며, 사용자가 다음 제안을 적용하고 읽기값이 일치해야 해제를 확인합니다.

`apply()`는 제안 생성 시점의 revision과 현재 revision을 비교합니다. 쓰기 뒤 읽기값이 요청과 일치해야 confirmed가 됩니다. operation 번호로 이전 요청의 종료가 새 요청의 busy를 해제하지 못하게 합니다. 수동 변경과 세션 변경은 이전 revision을 무효화합니다. 화면은 gateway의 내부 요청값 대신 최근 읽기값을 표시합니다.

`app.js`는 동일한 규칙 엔진을 DOM으로 보여 줍니다. 외부 서비스, 계정, 데이터 저장소가 없습니다. 새로고침하면 가상 데이터가 초기화됩니다.

Android는 Kotlin Activity 안의 WebView로 `web/` HTML/CSS/JS 네 파일과 공식 외관 JPEG 세 파일을 로드합니다. 허용 목록 밖의 요청과 외부 이동을 막으며 인터넷 권한·네이티브 JavaScript bridge가 없습니다. 현재 빌드는 제품용 차량 앱이 아닌 설치형 시뮬레이션입니다.

## 다음 검증 단계

공식 Pleos Emulator에서 공개 Vehicle SDK의 권한·capability·현재값 읽기·쓰기·변경 콜백을 검증해야 합니다. 실제 차량은 구역별 지원 범위가 다르므로 하드코딩한 시연 capability를 실제 조회값으로 대체하고, 차량 서비스 연결 및 앱 생명주기를 검증해야 합니다. STT/TTS, 학습 모델, 실제 사용자 성과는 아직 구현·측정하지 않았습니다.
